Firmware Scripts
================

This page talks about two programs:

1. **make-image**: Used to transform the TI .txt file created by CCS into a bootloader friendly .txt and .bin file format
2. **fw-upgrade**: Used to transfer the image generated by *make-image* into the node board via the RF or IR link

This doc assumes that you are generally familiar with the remote firmware upgrade process as explained in the high level document. This doc only talks about the implementation details in Python.


make-image
----------

This script is used for three purposes

1. Take as input the **node_fw TI .txt** file and create a file **out.bin** which is transferred to the external flash chip of the smart meter during remote firmware process.
2. Take as input the **node_fw TI .txt** file and create a file **out.txt** which can be burnt in the MSP430 microcontroller when the node_bsl bootloader has already been burnt in the microcontroller.
3. Take as input **node_fw TI .txt** file and **node_bsl TI .txt** file and create **out.txt** file which contains the programs present in both the input .txt files.

::

	usage: make-image [-h] [--bsl_file BSL_FILE] main_txt_file_path

	Creates image of new firmware forinfo flash

	positional arguments:
	  main_txt_file_path   Path to TI .txt file containing new firmware

	optional arguments:
	  -h, --help           show this help message and exit
	  --bsl_file BSL_FILE  Path to TI .txt file containing the BSL. Including this
	                       path indicates that the BSL code should be included in
	                       the .txt output file.



Sections & TI .txt File
+++++++++++++++++++++++

The TI .txt file has a similar format

::

	@1000
	30 40 2A 17 
	@1014
	3D 90 AD DE 04 20 3E 90 EF BE 01 20 03 3C 0C 43 
	0D 43 10 01 3C 41 3D 41 10 01 0C 43 2C D3 10 01 
	@104e
	2A 14 B1 00 AA 00 B2 40 80 5A 5C 01 B0 13 86 15 
	B0 13 4C 14 B0 13 9C 16 B0 13 82 12 CE 01 EE 03 
	B0 13 F4 13 CC 01 EC 03 B0 13 D2 16 CD 0C 8C 00 
	00 40 B0 13 D2 16 2A 00 0E 1C 29 42 1F 4A 08 00 

For example, the above content says that the 32 bytes from @1014 to @1034 are from 3D, 90 ... 10 01.

This representation allows for shorter file size for smaller programs. If the hex file format were to represent the exact memory map of the flash memory, then every TI .txt file would had data for 64 kBytes. Instead, the TI .txt file helps keep the file size small by only specifying data at relevant addresses.

In ``make_image.py``, the TI .txt file is frequently represented using the ``sections`` variable name. This variable is a dictionary indexed by address. 

::

	sections = {addr1: bytearray1, addr2: bytearray2 .. }

For example the above mentioned file would be represented in sections variable as follows:

::
	
	sections = {4096: bytearray('\0x30\x40\x2A\x17'), 4116: bytearray('\x2A...') ..}

.. autofunction::  gp_node.fw_upgrade.make_image.extract_sections

Example:

::

    string =["@0234",
             "D1 AD 05 00 3F 00 67 65 74 20 00 00 6E 65 74 77 ",
             "6F 72 6B 00 61 64 64 72 65 73 73 00 63 68 61 6E ",
             "@aa76",
             "3F 50 B8 00 81 4F 04 00 C1 4C 06 00 6D 49 1E 49 "]

Allocation Table
++++++++++++++++

The allocation table maps which data in the out.bin file corressponds to which locations in the MSP430 internal flash memory. The allocation table is a part of the header which is present at the top of the out.bin file. Refer to the high level document of remote firmware upgrade to get a better idea.

In ``make_image.py``, the allocation table is represented as a list of ``Row`` where ``Row`` is a named tuple

Using mspdebug
++++++++++++++

Download the latest version of mspdebug from http://mspdebug.sourceforge.net/. Download libmsp430 from https://github.com/BuLogics/libMSP430. Use ``make`` and ``sudo make install`` to install both these programs. The mspdebug version should be >= 0.22.

::
	
	mspdebug -d /dev/ttyACM0 tilib --allow-fw-update "prog some_file.txt"



Here, we list down the various action sequences to program the node board and the corressponding behavior.

**Case 1:** Burn node_bsl in Node using CCS; Burn node_fw in Node using CCS: When the firmware restarts, the bootloader will check for data integrity of the internal flash. Since the node_fw was burnt using CCS, the *allocation table* was not added in the image, hence node_bsl would assume that the internal image is corrupt and would check for a valid image in external flash.

**Case 2:** Burn node_bsl in Node using CCS; transform node_fw TI .txt file into out.txt file (using make-image) and burn it using mspdebug. This would work fine as the transformation would add the allocation table in the .txt file and the node_bsl bootloader will not complain

**Case 3:** Use make-image to combine node_bsl .txt file and node_fw .txt file to create out.txt file and then burn the out.txt file using mspdebug. Edit ``~/.mspdebug`` and add the entry ``opt enable_bsl_access true`` in it. This unlocks the BSL so that mspdebug can write/erase the BSL section of the microcontroller. Not use ``mspdebug`` as usual to program out.txt into the Node.


fw-upgrade
----------

The ``fw-upgrade`` program is a very simple script which transfers the **out.bin** file generated by ``make-image`` into the Node board using the Flash IO protocol. As of the present implementation, ``fw-upgrade`` broadcasts packets (ie, uses address 0.0.0.255); hence, it should either be used with the IR port or if it is being used over RF, then the network should only consist of one router and a gateway. It is trivial though, to extend fw-upgrade to use any other address.

::

	usage: fw-upgrade [-h] [-d DEVICE] [-b BAUD_RATE] [-p HEX_FILE]
	                       [-V VERSION]

	optional arguments:
	  -h, --help    show this help message and exit
	  -d DEVICE     device name, eg. /dev/ttyUSB0
	  -b BAUD_RATE  baud rate
	  -p HEX_FILE   programs new hex file
	  -V VERSION    options are 'live' and 'ext'
